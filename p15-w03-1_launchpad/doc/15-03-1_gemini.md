# Gemini

## 💡 MVP 공유 웹서비스 기획안

이 웹서비스는 사용자가 자신의 **개발 예정 제품 아이디어(MVP)**를 공유하고, 커뮤니티의 **피드백**을 받아 아이디어를 검증하며, 실제 MVP 개발과 최종 제품 런칭까지 연결하는 것을 목표로 합니다.

---

### 1. 🎯 서비스 목표 및 사용자

#### 서비스 목표

- **아이디어 검증:** 개발 전 시장과 잠재 고객의 반응을 빠르게 확인하여 개발 리스크를 줄입니다.
- **MVP 개발 촉진:** 좋은 피드백을 받은 아이디어의 개발을 격려하고 빠르게 MVP를 만들 수 있도록 돕습니다.
- **커뮤니티 형성:** 제품 개발에 관심 있는 기획자, 개발자, 잠재 사용자가 교류하는 장을 만듭니다.

#### 주요 사용자

- **아이디어 공유자 (Creator):** 제품 아이디어를 가지고 있으며 피드백을 원하는 기획자, 개발자, 스타트업 창업가 등.
- **피드백 참여자 (Feeder/Potential User):** 새로운 제품에 관심이 많고, 아이디어에 대한 건설적인 비판과 제안을 해줄 수 있는 잠재 사용자.

---

### 2. 📝 핵심 기능 및 워크플로우

|**사용자 유형**|**주요 활동**|**핵심 기능**|
|---|---|---|
|**아이디어 공유자**|아이디어 등록 및 관리, 피드백 확인, MVP 개발 진행 상황 업데이트|**아이디어 등록** (제목, 개요, 핵심 기능, 타겟 사용자, 원하는 피드백 유형), **MVP 로드맵/진행률 표시**, **피드백 분석 대시보드**|
|**피드백 참여자**|아이디어 탐색, 피드백 제공, '좋아요/싫어요', 후원|**아이디어 탐색/필터링**, **피드백 작성** (댓글, 점수 부여, 기능 제안), **MVP 개발 요청/지지 버튼** (Vote)|
|**공통**|사용자 간 소통, 알림 확인|**댓글/Q&A 기능**, **알림 기능** (새 피드백, MVP 런칭 등)|

#### 워크플로우 (아이디어 생명주기)

1. **아이디어 등록 단계:** 공유자가 웹서비스에 **MVP 아이디어**를 상세히 등록합니다.
2. **커뮤니티 피드백/검증 단계:**
    - 참여자가 아이디어를 검토하고 **건설적인 피드백**을 제공합니다 (댓글, 투표 등).
    - 일정 기간/투표수가 되면 **검증 완료**를 판단합니다.
3. **MVP 개발 시작 단계:**
    - 아이디어가 충분한 지지/좋은 피드백을 받으면, 공유자는 **MVP 개발 착수**를 선언하고, 진행 상황을 공유합니다.
4. **MVP 공유/테스트 단계:**
    - **개발된 MVP**의 링크를 커뮤니티에 공유하고, **베타 테스트**에 대한 추가 피드백을 받습니다.
5. **실제 제품 런칭 단계:**
    - MVP 테스트 결과를 바탕으로 최종 제품을 런칭하고, 웹서비스에 **런칭 완료**를 알립니다.

---

### 3. 🖥️ 화면 구성 (와이어프레임)

#### 1. 홈 화면

- **피드:** 최신/인기 **MVP 아이디어** 리스트를 제공합니다.
- **카테고리/태그 필터:** 관심 있는 분야의 아이디어를 쉽게 찾을 수 있도록 합니다.
- **MVP 개발 현황판:** 현재 커뮤니티에서 가장 많은 투표를 받은 아이디어나, 개발 중인 아이디어를 강조하여 보여줍니다.

#### 2. 아이디어 상세 페이지

- **아이디어 개요:** 제목, 목표, 타겟 사용자 등 핵심 정보.
- **피드백 영역:**
    - **건설적 피드백:** 댓글 및 Q&A 섹션.
    - **투표/지지:** 'MVP 개발 필요' 투표 버튼 (**Vote**) 및 '좋아요/싫어요'.
    - **후원 기능 (선택 사항):** 아이디어 개발을 응원하기 위한 작은 금액 후원 기능.
- **진행 상태 표시:** '아이디어 단계' → 'MVP 개발 중' → 'MVP 테스트 중' → '런칭 완료'.

#### 3. 마이페이지 (공유자 대시보드)

- 내가 등록한 아이디어 리스트 및 각 아이디어의 **피드백 통계** (투표수, 긍정/부정 피드백 비율 등).
- **MVP 개발 진행률** 업데이트 및 로드맵 관리 기능.

---

### 4. 💸 수익 모델 (장기적인 고려 사항)

- **프리미엄 기능:** 아이디어 공유자에게 더 심층적인 **피드백 분석 리포트**, 아이디어 **상단 노출 부스팅**, 또는 비공개 피드백 수집 기능 등을 유료로 제공합니다.
- **광고/제휴:** 개발 도구, 호스팅 서비스 등 개발 관련 기업의 광고를 유치합니다.
- **성공 수수료 (선택 사항):** 웹서비스를 통해 런칭에 성공한 제품에 대해 소액의 수수료를 받습니다.

---

### 5. 🚀 초기 MVP 개발 방향

초기에는 핵심 기능에 집중하여 빠르게 서비스를 런칭해야 합니다.

- **핵심 기능:** 아이디어 등록, 아이디어 목록 보기, 댓글 피드백 기능, 단순 투표 기능 ('개발해 주세요' 버튼).
- **디자인:** 사용자가 아이디어에 쉽게 집중하고 피드백을 남길 수 있도록 **간결하고 직관적인 UI/UX**에 초점을 맞춥니다.

#### FR 1. 아이디어 등록 및 관리 (Creator 전용)

|**ID**|**요구사항**|**설명**|**우선순위**|
|---|---|---|---|
|**FR 1.1**|아이디어 등록|제목, 개요(300자 제한), 상세 설명, 타겟 사용자, 핵심 기능 제안 등을 입력하여 게시글을 등록할 수 있어야 한다.|높음|
|**FR 1.2**|피드백 목표 설정|공유자가 아이디어를 등록할 때, '원하는 피드백 유형' (예: 디자인, 비즈니스 모델, 기술 스택)을 태그로 설정할 수 있어야 한다.|보통|
|**FR 1.3**|아이디어 수정/삭제|등록된 아이디어는 피드백이 일정 수 이하인 경우 공유자가 수정하거나 삭제할 수 있어야 한다.|높음|
|**FR 1.4**|진행 상태 업데이트|아이디어의 진행 상태를 '아이디어 단계' $\to$ 'MVP 개발 중' $\to$ '런칭 완료'로 변경할 수 있어야 한다.|높음|

#### FR 2. 아이디어 탐색 및 필터링 (Feeder/공통)

|**ID**|**요구사항**|**설명**|**우선순위**|
|---|---|---|---|
|**FR 2.1**|아이디어 목록 보기|홈 화면에서 등록된 모든 아이디어를 최신순, 인기순(투표수)으로 정렬하여 볼 수 있어야 한다.|높음|
|**FR 2.2**|검색 및 필터링|키워드 검색 및 '진행 상태', '카테고리', '원하는 피드백 유형(태그)'을 기준으로 필터링할 수 있어야 한다.|높음|

#### FR 3. 피드백 제공 및 투표 (Feeder 전용)

|**ID**|**요구사항**|**설명**|**우선순위**|
|---|---|---|---|
|**FR 3.1**|댓글 피드백 작성|로그인한 사용자는 아이디어 상세 페이지에서 건설적인 댓글 피드백을 작성할 수 있어야 한다.|높음|
|**FR 3.2**|MVP 개발 지지 투표|아이디어 당 1회에 한해 **'MVP 개발 요청 (Vote)'** 버튼을 클릭하여 아이디어를 지지할 수 있어야 한다.|높음|
|**FR 3.3**|피드백 수정/삭제|본인이 작성한 댓글은 언제든지 수정하거나 삭제할 수 있어야 한다.|높음|

#### FR 4. 사용자 인증 및 관리 (공통)

|**ID**|**요구사항**|**설명**|**우선순위**|
|---|---|---|---|
|**FR 4.1**|회원 가입/로그인|이메일/비밀번호 또는 소셜 로그인(예: Google)을 통해 가입 및 로그인할 수 있어야 한다.|높음|
|**FR 4.2**|마이페이지|사용자는 본인의 활동 내역(등록한 아이디어, 남긴 피드백, 투표한 아이디어)을 확인할 수 있어야 한다.|높음|

### 3. 🛡️ 비기능 요구사항 (Non-Functional Requirements)

|**구분**|**ID**|**요구사항**|**설명**|
|---|---|---|---|

||**NFR 2.2**|CSRF/XSS 방지|웹 애플리케이션 보안 취약점(CSRF, XSS)에 대한 방어책이 적용되어야 한다.|
|**사용성**|**NFR 3.1**|반응형 웹|서비스는 데스크톱, 태블릿, 모바일 등 다양한 기기에서 최적화된 화면을 제공해야 한다.|
||**NFR 3.2**|직관적인 UI|아이디어 등록 및 피드백 작성 과정이 복잡하지 않고 직관적이어야 한다.|
|**운영**|**NFR 4.1**|모니터링|시스템 로그 및 오류를 실시간으로 모니터링하고 추적할 수 있는 환경을 구축해야 한다.|

## 🛠️ MVP 공유 웹서비스 기술 스택 (로컬 환경 최적화)

기존 요구사항 명세서를 바탕으로, **클라우드 서비스 의존도를 최소화**하고 개발 및 테스트를 **로컬 환경에서 빠르고 효율적으로 진행**할 수 있도록 기술 스택을 최신 버전으로 업데이트하여 제안합니다.

---

### 1. ⚙️ 백엔드 및 데이터베이스 스택

|**구분**|**기술 스택**|**버전/특징**|**선택 이유**|
|---|---|---|---|
|**백엔드 (API 서버)**|**Node.js + Express**|Node.js (v20.x LTS), Express (v4.x)|자바스크립트 기반으로 프론트엔드와 언어 통일성이 높고, 가볍고 빠르게 API 서버 구축 가능.|
|**데이터베이스 (DB)**|**PostgreSQL**|최신 안정화 버전 (v16.x)|안정성이 높고, 복잡한 데이터 관계 및 쿼리 처리에 강력하며, 로컬 환경에서 Docker로 쉽게 실행 가능.|
|**ORM/ODM**|**Prisma**|최신 버전|TypeScript와 잘 통합되며, 직관적인 스키마 정의 및 마이그레이션 도구 제공.|
|**인증/보안**|**JWT (JSON Web Tokens)**|-|서버 자원 절약 및 Stateless 인증 구현에 용이.|

### 2. 🖥️ 프론트엔드 스택

|**구분**|**기술 스택**|**버전/특징**|**선택 이유**|
|---|---|---|---|
|**프론트엔드**|**React**|최신 버전 (v18.x)|가장 널리 사용되는 라이브러리로, 풍부한 커뮤니티와 개발 자료 확보 용이.|

|**타입스크립트**|**TypeScript**|최신 버전|대규모 프로젝트의 안정성 확보 및 유지보수성 향상. (백엔드/프론트엔드 모두 적용 권장)|

|---|---|---|---|

|**컨테이너 (로컬 DB)**|**Docker / Docker Compose**|-|로컬 환경에서 PostgreSQL DB를 **가상 환경에 격리**하여 쉽게 설치하고 관리할 수 있도록 함. 클라우드 없이 개발 환경 통일화에 필수적.|
|**버전 관리**|**Git**|-|협업 및 코드 변경 이력 관리를 위한 표준 도구.|

### 💡 로컬 환경 실행 계획 요약

1. **개발 환경 설정:** Node.js, Git, Docker가 로컬 PC에 설치되어 있어야 합니다.
    
2. **데이터베이스 실행:** Docker Compose를 사용하여 **PostgreSQL 컨테이너**를 로컬에서 실행합니다.
    
3. **백엔드 실행:** Express 서버를 로컬에서 실행하고, Prisma를 통해 DB 스키마를 동기화합니다.
    
4. **프론트엔드 실행:** React 애플리케이션을 로컬 개발 서버에서 실행하여 API 서버와 통신합니다.
    

이 스택은 MVP 개발에 최적화되어 있으며, 추후 사용자가 증가하여 클라우드 환경으로 전환할 때도 Node.js, React, PostgreSQL은 **대규모 서비스로의 확장성**이 충분합니다.
